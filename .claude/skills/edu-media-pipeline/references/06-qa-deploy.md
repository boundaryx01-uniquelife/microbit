# ⑥ 점검·배포·운영 검증

## 완성도 점검(배포 전, 병렬 3명)
기술 QA / 사용자 관점 / 저장소 정리를 하위 에이전트로 동시에(⑤ 표 참고). 결과를 받으면:
1. 확인된 문제와 추측을 나눈다. 병렬 실행 테스트 실패는 직렬로 재현될 때만 문제로 본다.
2. 실제 문제만 고치고, 지울 파일은 **목록을 보여 주고 사용자 승인 후** 지운다(다른 세션·사람이 만든 실험 파일이 섞여 있을 수 있음). 지우기 전 참조 재확인(`grep`), 주석 속 언급은 고친다.
3. 문서 최신화: README "자료 다시 만들기"(각 도구 실행법), 테스트 목록·항목 수(실제 실행 결과로), 검증 보고서에 날짜 절 추가.

## 배포(Git → Netlify 예)
1. 작업 브랜치에 커밋·푸시 → PR(템플릿 있으면 따름) → 미리보기 주소에서 핵심 테스트.
   - 미리보기 전용 협업 도구 iframe의 CSP 경고는 운영에 없으니 제외.
2. 병합(squash). 병합한 브랜치에 이어서 작업할 때는 기본 브랜치를 먼저 합치고(`git diff`로 내용 동일 확인), 강제 푸시는 쓰지 않는다.
3. **운영 반영 확인**: 새 파일 존재/삭제 파일 404, 바뀐 파일 크기 비교, 운영 주소로 핵심 테스트.
   - 바로 안 바뀌어도 서두르지 않는다: 빌드 대기열 때문에 수십 분 늦을 수 있다. 배포 목록(Netlify Deploys/Activity — 사용자 로그인 필요, 캡처 요청)에서 그 커밋의 빌드가 대기·진행·완료·실패 중 무엇인지 먼저 본다. 목록에 없거나 실패일 때만 Netlify MCP `deploy-site`로 직접 배포. '자동 배포가 꺼졌다'는 목록으로 확인하기 전에는 말하지 않는다.
   - 배포 CLI가 만든 `.netlify/`는 `.gitignore`에.
4. 다른 사람·세션이 그사이 기본 브랜치에 올린 커밋이 있으면, 내 변경이 살아 있는지 확인(로고·아이콘·CSS 규칙 grep, PPT 속 이미지 해시).
